# CICD Work Reference

Use this reference for `agentia cicd work ...`, `agentia cicd cloud ...`, and matching MCP tools such as `agentia_work_get`, `agentia_cloud_commit_context_set`, `agentia_cloud_commit`, `agentia_work_publish`, and `agentia_work_submit`.

## Current Story Context

Treat these as requests for the locally active Copado user story (from a prior `work set`), not a specific ID the user supplied:

- current story, current user story, active story, this story
- story context, work item context, what story am I on

**Resolve before continuing** (status updates, publish/submit, deployment steps, promotions tied to “this” story, and similar):

```sh
agentia cicd work get --json
```

Omit the positional story ID only; keep `--json` so agents parse the `result` object. With MCP, call `agentia_work_get` without an `id` when available.

**On success:** treat the JSON `result` user story as the story context for the rest of the task. Reuse any returned fields later commands or flags need (identifiers, names, status, acceptance criteria, functional or technical specs, pipeline or environment references, subscriber `customFields`, and similar)—not only `id` and `name`.

**On failure:** the CLI exits when no active work item is recorded (typical message: no active work item). After `agentia cicd workflow get --json`, suggest `agentia cicd work set <id>` when the lock is `local` or unset, or `agentia cicd cloud set <id>` when the lock is `cloud`. Tell the user that no current story is set, include the sanitized error text, and stop. Do not invent an ID, run `work list` to pick one, or continue the original request until the user sets context or provides an explicit story ID.

## Choose One Workflow

Local and cloud work are separate delivery paths. Do not continue a cloud commit with local `work publish` or `work submit`: those commands inspect and push the local Git feature branch.

Before starting delivery, read the lock with `agentia cicd workflow get --json` (MCP `agentia_workflow_get`). Honor that value: `local` → Local Repository Flow only; `cloud` → Copado Cloud Flow only; unset → either path is allowed for the task. Do **not** call `workflow set` or `workflow unset` yourself while following a flow—only the user (or an explicit request) changes the lock. Project value lives in `.agentia/config.user.json`; `--global` uses `~/.config/agentia-cli/config.json` (project user wins). When `cloud` is set, local delivery mutators (`work publish`/`push`/`submit`/`done`, `work promote`, `work environment-sync`, local `work set`, hidden `work commit`) error. When `local` is set, `cloud set`, `cloud changes list`, `metadata list --include-local` / MCP `includeLocal`, and all `cicd cloud *` commit/promote/commit-context/selective-commit commands error.

### Local Repository Flow

Use this path when the change exists in the local repository (and `workflow get` is `local` or unset):

1. Discover and inspect: `agentia cicd work list --assigned-to-me --json`, then `agentia cicd work get <id-or-name> --json`.
2. Activate: `agentia cicd work set <id-or-name> --json`. This fetches the configured base branch, fetches the Story feature branch when it exists on origin, then checks out `feature/<story-name>` from that remote branch when present (otherwise from the base), and records the story, base branch, dev org branch, and pull-request context in `.agentia/config.user.json`. Use `--base-branch <branch>` only when intentionally overriding the Pipeline default. If the JSON result has `status: "warning"` (missing pipeline or credential), show that `message`, do not assume a feature branch was created, and note that branch keys (`lastBaseBranch`, `lastDevOrgBranch`, `lastPullRequestBaseUrl`) were cleared while `lastWorkItemId`/`lastWorkItem`/`lastWorkItemTitle` were recorded — stop until the Story setup is fixed; publish and submit will not work. If the Story source credential differs from the project default, work set warns with the current credential and environment and does not PATCH; use `agentia cicd work update <id> --source-credential <credential-id>` to change it.
3. Implement with Salesforce CLI, VS Code, or an IDE. Stage and commit with `git add` / `git commit`. Do not use `agentia cicd cloud commit` for local Git work.
4. Run project-owned gates: `agentia cicd work test --json`. This runs `.agentia_quality_gates.sh` or `.agentia_quality_gates.cmd` from the repository root when present. If those files are missing, it warns and runs the stock sample from a temporary file. Local tests can be slow; pass `--apex-test-classes=MyTest,OtherTest` for faster, earlier Apex checks.
5. Register and synchronize: `agentia cicd work publish --json`. A plain `git push` does not register a Copado Commit or merge the feature branch into the recorded dev org branch. Pass `--permissions` and `--full-metadata` when nested detection is not enough.
6. Validate and open the merge-request flow: `agentia cicd work submit --json`. Submit runs the local gates unless `--skip-local-tests` is explicit, pushes ahead commits, waits if the last pending related job is a Commit template, and submits with validate-only behavior. `--skip-pull-request` skips opening the compare URL.
7. Only with explicit approval to promote and deploy, run `agentia cicd work submit --deploy --json` (or `--done`). `work done` is a compatibility alias.
8. Check asynchronous results with `agentia cicd work status [id-or-name] --json` and use `jobs[].id` (JobExecution Id) for `job get` / `job log get`—not the headless `jobId` on publish/submit/done responses.

`work set`, `work publish`, and `work submit` require a clean tracked working tree. `work publish` also requires the exact `feature/<story-name>` branch, recorded `lastBaseBranch` and `lastDevOrgBranch`, and at least one commit in `origin/<lastBaseBranch>..HEAD`. `work submit` fetches `origin/<lastBaseBranch>` and permits an empty commit range only for a Story with a Salesforce Data Set or Data Template deployment step.

### Copado Cloud Flow

Use this path when Copado should retrieve metadata from a configured source environment instead of using local Git changes (and `workflow get` is `cloud` or unset):

1. **Required — set the active work context:** `agentia cicd cloud set <id> --json` (MCP `agentia_cloud_set`). This defines the current Story for the cloud path (no Git checkout). It reuses the Gateway work/set request, clears local-delivery-only keys, refreshes `lastCloudCommitContext`, writes `lastCloudChangeMarker` (ISO timestamp, scoped by `lastWorkItemId`) into `.agentia/config.user.json`, and returns `deliveryFlow: "cloud"`. Each cloud set refreshes the marker to now. Do not skip this step. On success human output notes that local source changes are tracked from now (and how to list them); a gateway warning still attempts commit-context refresh.
2. **Only when step 1 warned that commit context was missing:** fix the User Story (credential/environment/pipeline readiness as reported), then run `agentia cicd cloud commit-context set --json` (active Story only; no Id; hard-fails on error). Inspect with `agentia cicd cloud commit-context get --json` when useful. Skip this step when `cloud set` already refreshed context successfully.
3. **Implement the change in the source org:** use Salesforce CLI, VS Code, an IDE, or the Salesforce UI to create or edit metadata in the Story’s source environment. Local files may mirror those edits for reference, but cloud delivery commits from the org—not via `git commit` / `work publish`.
4. **Identify what to commit (index, org content, compare, and/or local files):** Prefer offline local discovery when local source mirrors org edits: `agentia cicd cloud changes list --json` (MCP `agentia_cloud_changes_list`) lists pending local files since `cloud set` (mtime at or after `lastCloudChangeMarker`) without a gateway call. Or add local pending changes with `agentia cicd metadata list --include-local --json` (MCP `includeLocal`), which keeps gateway `data`/counts unchanged and adds a separate `local` block. You can still mix: local Salesforce source files; `agentia cicd metadata content get ... --json`; `agentia cicd metadata content compare ... --json`; and the index via `agentia cicd metadata list --json` (pipeline/credential optional when `lastCloudCommitContext` or project defaults exist). To list metadata already committed on the Story as index-shaped rows, use `agentia cicd metadata list --source PreviouslyCommitted [--user-story-id <id>] --json` (MCP `source: PreviouslyCommitted`, optional `userStoryId`; defaults to the active work item). That path GETs committed-metadata and rejects other index filters/context flags; it is separate from `work get --committed-metadata`, which returns a slim `{action, category, name, type}` list. When the source environment has source tracking enabled, pass `--source-tracking-enriched` so newer org changes still appear from the org’s source tracker even if the Copado index is outdated. If the index still looks stale or empty (or source tracking is not available), refresh it with `agentia cicd metadata refresh run --source-credential-id <id>` (default `--refresh-mode ALL`; use `CUSTOM` with `--selected-type` for type-scoped refresh), then check `metadata refresh status` as needed and list again. Use `agentia cicd metadata type list --json` and `agentia cicd metadata user list --json` to extract types and users from that index; use `agentia cicd metadata bundle list --metadata-type ... --api-name ... --json` when you need a bundle’s internal member structure for a partial selection. Context for list/type/user/bundle resolves atomically (explicit credential/pipeline → active-Story commit context → project defaults); org Id is derived internally.
5. **Only when a metadata item must be partially committed:** create/get an opaque selective-commit session with `agentia cicd cloud selective-commit create --metadata-type <type> --api-name <name> [--member-path <relative-path>] --file <content> --json` and `agentia cicd cloud selective-commit get <session-id> --json` (returns Id/hash only; `--member-path` is required for bundles and omitted for non-bundle types; `--file` is raw edited content, not a JSON envelope). Skip this when committing whole metadata items.
6. **Cloud commit:** `agentia cicd cloud commit <story-id> ... --json`. Use the simple metadata flags for one change, or `--file`/`--stdin` for a multi-change request. Always pass `--metadata-category` (use `SFDX` for Salesforce metadata). With `--file`/`--stdin`, each change requires `c` (or `category`). The command waits for its Job Execution by default; after a timeout, follow with `agentia cicd job get` / `job log get` using `jobExecution.id` from the commit response—do not immediately submit a duplicate commit. Local change listing is relative to the latest `cloud set` marker time.
7. **Cloud promote (when explicitly approved):** `agentia cicd cloud promote <story-id> --json`; add `--deploy` only for promote-and-deploy. Creates a forward Draft promotion when none contains the story (`createdPromotion` in JSON/MCP). This is independent of local `work submit`.

Cloud commit checks Story readiness and source credentials before submission. Avoid concurrent cloud commits to one Story. Treat `--recreate-feature-branch` as destructive because it can overwrite Story-branch work.

## Local Repository Details

Use Git for normal source changes:

```sh
git add -A
git commit -m "US-0001 add account service"
agentia cicd work test --json
agentia cicd work publish --permissions CustomField:Account.SLA__c,ApexClass:AccountService --json
agentia cicd work submit --json
```

`--permissions` on publish names metadata that Copado should treat as Retrieve Only. List the components whose access changed, not the permission set or profile files; naming those parent types is rejected. Use `--full-metadata` only for `Profile`, `PermissionSet`, `MutingPermissionSet`, `CustomObject`, or `CustomObjectTranslation` when that complete file should travel; other types are rejected. Both flags apply to that publish only.

`work test` and `work submit` take `--apex-test-classes` when you want the local gate script to receive them as `AGENTIA_APEX_TEST_CLASSES`. Sample quality-gate scripts pass that value to the apex gate (`work test --gate apex`). Run one gate with `work test --gate lint` (MCP `gates: ["lint"]`); `work submit` always runs every gate. The sample lint gate scans only branch-changed files (diff vs `AGENTIA_BASE_BRANCH` merge-base, plus uncommitted/untracked); set `LINT_SCOPE=all` for a full scan, which is also the fallback outside git.

`work publish` detects nested metadata across the full branch diff from the merge base to `HEAD`, applies Copado environment-variable and YAML replacements, registers every commit in the range, and merges into the recorded dev org branch. Review unexpected Retrieve Only, Full Metadata, or nested-deletion output before continuing.

## Cloud Operation Details

Use cloud commits when Copado should retrieve metadata itself:

```sh
agentia cicd cloud commit <story-id> --message "Commit AccountService" --metadata-name AccountService --metadata-type ApexClass --metadata-category SFDX --json
agentia cicd cloud commit <story-id> --file commit-request.json --json
```

`--metadata-category` is required on simple flag input. For Salesforce metadata, use `SFDX`. Without `c:SFDX`, Copado deploy logs can report "Salesforce changes not found."

`--file` / `--stdin` JSON request attributes:

| Field                                                  | Required                      | Notes                                                  |
| ------------------------------------------------------ | ----------------------------- | ------------------------------------------------------ |
| `message`                                              | yes\*                         | Commit message (`*` unless also passed as `--message`) |
| `changes`                                              | yes                           | Array of change objects (below)                        |
| `userStoryId` / `user_story_id`                        | no                            | Defaults to positional Id or active work item          |
| `baseBranch` / `base_branch`                           | no                            | Base branch included in the request                    |
| `executeCommit` / `execute_commit`                     | no                            | Default `true`; run the Copado commit job              |
| `commitId` / `commit_id`                               | when `executeCommit` is false | Existing local Git commit to register                  |
| `recreateFeatureBranch` / `recreate_feature_branch`    | no                            | Default `false`                                        |
| `dataTemplateSyncConfig` / `data_template_sync_config` | no                            | Data-template sync payload when applicable             |

Each `changes[]` entry (short alias or long name):

| Field                        | Required                    | Notes                                                         |
| ---------------------------- | --------------------------- | ------------------------------------------------------------- |
| `a` / `action`               | yes                         | `Add`, `Delete`, `RetrieveOnly`, `SelectiveCommit`, or `Full` |
| `n` / `name`                 | yes                         | Metadata API name / full name                                 |
| `t` / `type`                 | yes                         | Metadata type (for example `ApexClass`)                       |
| `c` / `category`             | yes                         | Use `SFDX` for Salesforce metadata                            |
| `m` / `message`              | no                          | Per-change message                                            |
| `j` / `rawJson` / `raw_json` | no                          | Optional raw metadata JSON for the change                     |
| `selections`                 | for SelectiveCommit bundles | Relative member paths inside the bundle                       |

Example single-component request:

```json
{
  "message": "Commit AccountService",
  "changes": [{"a": "Add", "c": "SFDX", "n": "AccountService", "t": "ApexClass"}]
}
```

Example multi-component `commit-request.json`:

```json
{
  "message": "Account service and trigger",
  "changes": [
    {"a": "Add", "c": "SFDX", "n": "AccountService", "t": "ApexClass"},
    {"a": "Add", "c": "SFDX", "n": "AccountTrigger", "t": "ApexTrigger"}
  ]
}
```

`--metadata-category` is required on simple flag input (one component only). Each `--file`/`--stdin` change requires `c` (or `category`). For Salesforce metadata, use `SFDX`. Without `c:SFDX`, Copado deploy logs can report "Salesforce changes not found."

For cloud promotion from a User Story:

```sh
agentia cicd cloud promote <story-id> --json
agentia cicd cloud promote <story-id> --deploy --json
```

When no Promotion contains the story, `cloud promote` and MCP `agentia_cloud_promote` create one automatically before running.

Cloud commit and promotion wait for Job Executions by default and return nonzero on failed or timed-out jobs while preserving diagnostic IDs. If a Promotion reaches Merge Conflict, resolve it and resume the original execution; do not start a replacement run.

## Subscriber Custom Fields

Org-defined User Story fields (API names ending in `__c`, excluding packaged `copado__*`) are exposed as `customFields` on `work get` / create / update responses.

- **Read:** prefer `agentia cicd work get [id] --json` (or MCP `agentia_work_get`) and use `result.customFields`. Prefer `displayValue` when presenting values; use `apiName` when writing. Human output lists them under `Custom Fields:` after `Components:`.
- **Write (CLI):** repeatable `--custom-field ApiName=value` (string values; first `=` splits key/value). Duplicate `apiName` values are rejected.
- **Write (MCP):** `customFields: [{ "apiName": "JIRA_Key__c", "value": "CICD-1" }]` on `agentia_work_create` / `agentia_work_update` (values may be string, number, boolean, or null).
- Omit custom-field flags/args for packaged-only mutations. Unknown or non-updateable names fail with gateway `PLA-US-009`.

```sh
agentia cicd work create --title "Story" --custom-field JIRA_Key__c=CICD-1 --json
agentia cicd work update --custom-field Priority_Pick__c=P1 --json
agentia cicd work get --json
```

## Deployment Steps

Deployment steps are attached to a user story and run during promotion.

| Command                                 | Use For                                                                                           |
| --------------------------------------- | ------------------------------------------------------------------------------------------------- |
| `work deployment-step types`            | List supported standard/custom step types.                                                        |
| `work deployment-step salesforce-flows` | List directly invocable Salesforce Flows.                                                         |
| `work deployment-step list`             | Inspect current story steps.                                                                      |
| `work deployment-step create`           | Add Manual Task, Salesforce Flow, Function, Apex, Data Set, Data Template, or Robotic Test steps. |
| `work deployment-step update`           | Apply sparse step updates.                                                                        |
| `work deployment-step reorder`          | Submit a complete before/after ordering snapshot from file or stdin.                              |
| `work deployment-step delete`           | Delete an owned step by ID.                                                                       |

Prefer explicit flags for standard step types. Use `--config-json` or `--config-file` on create/update when the step needs expert configuration not covered by flags; only `deployment-step reorder` accepts `--file` or `--stdin`. Read `types` first when unsure.

## Gotchas

- `work test` is not CRT. For Robot Framework execution, use the `agentia-testing` skill.
- `work test apex` (same run as `work test --gate apex` alone) runs named Apex classes directly. Sample local quality gates (`.agentia_quality_gates.*`) call it with `--apex-test-classes="${AGENTIA_APEX_TEST_CLASSES}"` and `${AGENTIA_APEX_RERUN_FAILED}` (empty or `--rerun-failed-apex-tests`); an empty class list skips Apex without failing the script. `--rerun-failed-apex-tests` reruns classes saved in `.agentia/apex.tests.<user-story>.json` after a failure. Run it directly for a targeted rerun without the rest of the gates.
- A real Apex run (direct, or a gate run by `work test`) also publishes to the story: the classes it ran are added to the story's Apex test selection (add-only, never removed) and the story Apex coverage fields are written with the DX math, from whatever the run covered (for example one `--apex-test-classes` class). Nothing is written while a commit job runs, without an Apex Test record, or without committed Apex; the reason is printed and `--json` returns it under `apexPublish`. Direct runs and gate runs inside a script (which leave the Local Quality Gate result upload to the outer run) publish immediately and are also cached; `work publish` re-applies the cached run after the commit job, since the commit resets the coverage fields. `work submit` / `work done` never write coverage; the gates `work submit` runs skip the Apex publish.
- Local Git work uses `git commit` then `work publish`. Cloud `cloud commit` is a separate path.
- `work submit` may push ahead commits, but the local flow still needs story and branch context from `work set`.
- `work submit --done` (or `--deploy`) promotes/deploys. Do not run it unless the user explicitly asked to promote or finish the story.
- `cloud promote` is not the next step after a local git commit; local delivery uses `work publish` and `work submit`.
- `work delete` is destructive; read the story and confirm intent first.
